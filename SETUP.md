# Local development

Install R (4.1+), `facereaderconverter` (tested against 0.3.2.1), and the R packages `shiny`, `bslib`, `markdown`, `zip`, `callr`, and `later`. The converter's own dependencies are installed with it. Install FFmpeg **and** FFprobe separately in the project-root `bin/` directories described in [bin/README.md](bin/README.md); the executables are not stored in Git. Their download URLs, hashes, and verification status are in [bin/SOURCES.md](bin/SOURCES.md). Do not distribute a desktop build until GPL/source and codec/patent obligations are reviewed and the Linux/macOS bundles have been tested on their target machines.

Launch from the project root with `shiny::runApp('.')`. For the optional desktop shell, install Node.js and run `npm install` then `npm run desktop` from the same root. Electron uses the Rscript executable on PATH (or `RSCRIPT` environment variable), starts Shiny bound to `127.0.0.1`, and requires the R packages and platform media binaries to be installed separately.

## Windows x64 bundle

From a Windows terminal in the project root, install Node.js and R, plus the app's R packages listed above (and `markdown`, `readr` and `readxl`). Run `npm ci`, then `npm run bundle:win`; this downloads and verifies the current Windows media tools and writes `SOURCE-NOTICE.md`, `MEDIA-PROVENANCE.json` and `COMPONENT-INVENTORY.json` in the development folder. For development without bundling, run `npm run download:media:win`. The script [electron/bundle-win.js](electron/bundle-win.js) stages the installed R and its package dependencies, builds the Electron desktop folder, runs the isolated R/Shiny startup smoke test, and copies [run instructions](electron/RUN-BUNDLE.md). Only an approved release run creates `dist/library-of-happy-moments-win-x64.zip`. Set `BUNDLE_RSCRIPT` to the intended `Rscript.exe` path if multiple R versions are installed. This builds from locally installed R/packages: use the same R and R package versions on each build machine for repeatable inputs (there is not yet an R dependency lockfile). Extract the **whole** release ZIP on Windows x64 and run `win-unpacked/Library of Happy Moments.exe`; no R or Node.js installation is needed on the recipient machine. This is a portable folder, not a single-file EXE or installer.

**Do not distribute the output yet.** `npm run bundle:win` creates a local development folder but withholds the ZIP unless both `MEDIA_ASSET_SHA256` (the upstream asset's pinned `sha256:<64 lowercase hex>` digest) and `RELEASE_REVIEW_FILE` (path to a release review JSON file) are set. Inspect `dist/win-unpacked/COMPONENT-INVENTORY.json` first. The review file must include `inventorySha256` (SHA-256 of that file), `mediaAssetDigest`, `mediaFileHashes` for both executables, and nonempty `mediaCorrespondingSource`, `rAndPackageSources`, `electronChromiumSources`, `licenseNoticeReview`, and `codecPatentReview` fields. Obtain and document exact matching source/build inputs, required notices and a real recipient-access route; record qualified license and territory-specific patent review. Then set the digest and review file variables and run `npm run release:win` to verify and ZIP the **same staged folder** without downloading anything again. A changed input invalidates the review. The review fields record human decisions, not automated legal clearance. An upstream URL or a filled-in placeholder does not meet source obligations. The app's `LICENSE` covers its R scripts under MIT; separately bundled FFmpeg, R, R packages, Electron and Chromium retain their own licenses. Never represent a successful smoke test or emitted ZIP as proof of compliance.

### Release steps (Windows x64)

Run these in a Windows cmd terminal from the project root. Steps 4 to 6 are human review work; the scripts only check that the review fields are present and match the staged binaries.

1. **Pin the media build.** Decide which upstream FFmpeg asset to ship (`ffmpeg-n9.0-latest-win64-gpl-9.0.zip` from BtbN/FFmpeg-Builds; the `latest` tag moves, so the digest changes between upstream rebuilds). Take its `sha256:<64 hex>` digest from the upstream release page and run `set MEDIA_ASSET_SHA256=sha256:<digest>` without quotes. Check it with `echo %MEDIA_ASSET_SHA256%`. The download step aborts if upstream's current asset differs from the pin.
2. **Build the folder without the ZIP.** Leave `RELEASE_REVIEW_FILE` unset and run `npm ci`, then `npm run bundle:win`. This produces `dist/win-unpacked/` with `SOURCE-NOTICE.md`, `MEDIA-PROVENANCE.json` and `COMPONENT-INVENTORY.json`, and withholds the ZIP.
3. **Test the folder.** Follow [Manual local bundle for testing only](#manual-local-bundle-for-testing-only).
4. **Archive the corresponding source** for the exact FFmpeg build (FFmpeg commit shown in `ffmpeg -version`, the BtbN build scripts, and x264), plus R, package and Electron/Chromium sources, in a location recipients can actually reach. A link to upstream alone does not meet the source obligation for a moving tag.
5. **Write the review file outside `dist/`**, for example `release-review.json` in the project root. It needs five nonempty statements (`mediaCorrespondingSource`, `rAndPackageSources`, `electronChromiumSources`, `licenseNoticeReview`, `codecPatentReview`), each naming the reviewer, date, evidence location and outcome, plus the hash fields: `inventorySha256` (SHA-256 of `dist/win-unpacked/COMPONENT-INVENTORY.json`), `mediaAssetDigest`, and `mediaFileHashes` for `ffmpeg.exe` and `ffprobe.exe`, all copied from that inventory. Get the licence and territory-specific patent (H.264) review from a qualified person before external distribution.
6. **Release.** Run `set RELEASE_REVIEW_FILE=<full path to the review file>` and `npm run release:win`. It re-checks the digest, re-audits the folder, verifies the review evidence and writes `dist/library-of-happy-moments-win-x64.zip`.

Re-running `npm run bundle:win` regenerates the inventory, so update `inventorySha256` in the review file after any rebuild. Do not zip `dist/win-unpacked` by hand for anything that leaves the team, because that bypasses the checks above.

### Manual local bundle for testing only

Use this workflow only to build and test the Windows x64 desktop app locally. It is **not a release or redistribution process**; do not send or publish the generated files. From a Windows x64 terminal in the project root, install dependencies with `npm ci`, then run `npm run bundle:win`. Leave both `MEDIA_ASSET_SHA256` and `RELEASE_REVIEW_FILE` unset: the script creates `dist/win-unpacked/`, runs the bundled R/Shiny startup smoke test, and withholds the ZIP. If both variables are set, the script may also proceed to release packaging, so do not set them for this test-only workflow.

To test the built app, open `dist/win-unpacked/Library of Happy Moments.exe` and check that it starts and can process a representative local input. You can rerun the startup smoke test with `npm run test:bundle`. Keep the entire `win-unpacked` folder together. These local checks do not complete release review, establish legal compliance, or authorize distribution.

Upload one video (`mp4`, `mov`, `mkv`, `avi`) and exactly two detailed FaceReader exports (`txt`, `xlsx`) whose `Filename` metadata matches the video. Click Process video; sort the resulting clips by time or selection rank and navigate with the arrows. The download button creates a ZIP with clips and their manifest; media files live in session temporary storage and are removed on disconnect. For sensitive recordings, use only a trusted local machine; this scaffold has no authentication and should not be exposed as a public server.

Run focused helper tests using `testthat::test_file('tests/testthat/test-0100-app-helpers.R')`; run release checks using `npm run test:media`. Larger videos may require raising `shiny.maxRequestSize` in `app.R`.
