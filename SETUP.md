# Local development

Install R (4.1+), `facereaderconverter` (tested against 0.4), and the R packages `shiny`, `bslib`, `zip`, `callr`, and `later`. The converter's own dependencies are installed with it. Install FFmpeg **and** FFprobe separately in the project-root `bin/` directories described in [bin/README.md](bin/README.md); the executables are not stored in Git. Their download URLs, hashes, and verification status are in [bin/SOURCES.md](bin/SOURCES.md). Do not distribute a desktop build until GPL/source and codec/patent obligations are reviewed and the Linux/macOS bundles have been tested on their target machines.

Launch from the project root with `shiny::runApp('.')`. For the optional desktop shell, install Node.js and run `npm install` then `npm run desktop` from the same root. Electron uses the Rscript executable on PATH (or `RSCRIPT` environment variable), starts Shiny bound to `127.0.0.1`, and requires the R packages and platform media binaries to be installed separately.

## Windows x64 bundle

From a Windows terminal in the project root, install Node.js and R, plus the app's R packages listed above (and `readr` and `readxl`). Run `npm ci`, then `npm run bundle:win`; this downloads and verifies the current Windows media tools and writes `SOURCE-NOTICE.md`, `MEDIA-PROVENANCE.json` and `COMPONENT-INVENTORY.json` in the development folder. For development without bundling, run `npm run download:media:win`. The script [electron/bundle-win.js](electron/bundle-win.js) stages the installed R and its package dependencies, builds the Electron desktop folder, runs the isolated R/Shiny startup smoke test, and copies [run instructions](electron/RUN-BUNDLE.md). Only an approved release run creates `dist/library-of-happy-moments-win-x64.zip`. Set `BUNDLE_RSCRIPT` to the intended `Rscript.exe` path if multiple R versions are installed. This builds from locally installed R/packages: use the same R and R package versions on each build machine for repeatable inputs (there is not yet an R dependency lockfile). Extract the **whole** release ZIP on Windows x64 and run `win-unpacked/Library of Happy Moments.exe`; no R or Node.js installation is needed on the recipient machine. This is a portable folder, not a single-file EXE or installer.

**Do not distribute the output yet.** `npm run bundle:win` creates a local development folder but withholds the ZIP unless both `MEDIA_ASSET_SHA256` (the upstream asset's pinned `sha256:<64 lowercase hex>` digest) and `RELEASE_REVIEW_FILE` (path to a release review JSON file) are set. Inspect `dist/win-unpacked/COMPONENT-INVENTORY.json` first. The review file must include `inventorySha256` (SHA-256 of that file), `mediaAssetDigest`, `mediaFileHashes` for both executables, and nonempty `mediaCorrespondingSource`, `rAndPackageSources`, `electronChromiumSources`, `licenseNoticeReview`, and `codecPatentReview` fields. Obtain and document exact matching source/build inputs, required notices and a real recipient-access route; record qualified license and territory-specific patent review. Then set the digest and review file variables and run `npm run release:win` to verify and ZIP the **same staged folder** without downloading anything again. A changed input invalidates the review. The review fields record human decisions, not automated legal clearance. An upstream URL or a filled-in placeholder does not meet source obligations. The app's `LICENSE` covers its R scripts under MIT; separately bundled FFmpeg, R, R packages, Electron and Chromium retain their own licenses. Never represent a successful smoke test or emitted ZIP as proof of compliance.

Upload one video (`mp4`, `mov`, `mkv`, `avi`), or use **Advanced options > Multi-video > Add video** repeatedly for further camera views, and exactly two shared detailed FaceReader exports (`txt`, `xlsx`). The Multi-video panel also contains **Audio source**, **Duration tolerance (milliseconds)** and **Playback columns**; its reset removes extra video inputs and restores these defaults while retaining the initial video and shared exports. Videos must already share their starting point. **Audio source** defaults to the first video added and selects the sole audio track for playback and export; its filename is used for the FaceReader metadata checks. Missing audio means silence. Duration differences greater than **Duration tolerance (milliseconds)** block processing; the default is zero for exact matching. Accepted differences use the shortest video timeline. Click Process video; sort the resulting synchronized clip sets by time or selection rank and navigate with the arrows. **Playback columns** defaults to two, is configurable, and collapses on narrow screens. The download creates a ZIP with a fixed two-column composite per moment and `manifest.csv`; single-video exports remain full-frame. Changing uploads, the audio source or tolerance invalidates generated results. Media files live in session temporary storage and are removed on disconnect. For sensitive recordings, use only a trusted local machine; this scaffold has no authentication and should not be exposed as a public server.

The same duration tolerance checks both FaceReader exports against every video, including single-video sessions. An export's duration is its final `Video Time` plus one frame at its declared frame rate. The maximum difference across the video and export durations must be within the tolerance; missing or invalid timestamps are blocking errors. The accepted playback/export timeline still ends at the shortest video.

In Advanced options → Clip export, **Optimised subject** lists the subjects parsed from the uploaded exports, using the same precedence as the converter: Subject mapping CSV, loaded `participant_name`, then the staged filename (if filename fallback is enabled). Names are matched literally, including punctuation; no regex entry is needed. **Both subjects (combined)** remains the default and keeps combined synchrony ranking, even when Only synchronies is unchecked. Selecting one subject ranks synchronies by that subject's value when Only synchronies is checked, or selects that subject's episodes when unchecked. Duplicate or unresolved subjects require a unique mapping or corrected exports. If an upload or mapping changes the selected name, select again rather than silently switching to both. Errors shown in the app omit ANSI colour codes; diagnostic console output is unchanged.

Run focused helper tests using `testthat::test_file('tests/testthat/test-0100-app-helpers.R')`; run release checks using `npm run test:media`. Larger videos may require raising `shiny.maxRequestSize` in `app.R`.

Run subject-selector regressions with `testthat::test_file('tests/testthat/test-0126-subject-selection.R')`. These use synthetic data, not participant recordings. The XLSX case requires the optional test package `openxlsx`; the Process video integration case requires the bundled FFmpeg/FFprobe tools. Those cases skip if their dependencies are unavailable.

Run multi-video regressions with `testthat::test_file('tests/testthat/test-0127-multi-video.R')`; the media cases use synthetic videos and require the platform FFmpeg/FFprobe pair. Browser coordination checks use `node --test tests/multi-video.test.js`. Windows packaging accepts verified media provenance from the original BtbN/FFmpeg-Builds repository and its successor FFmpeg-Builds/FFmpeg-Builds; checksums and the human release-review gates are unchanged.
